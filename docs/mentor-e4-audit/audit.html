Two solid tools with three wrong answers and no morning list

Both mentor surfaces are well built and don't need a redesign. But some of their logic gives mentors wrong answers. And nothing tells a mentor who needs them today. This page lists what I found, proposes the one new screen (今日) that the AI check-ins need, and shows how to test all of it on localhost before anything ships.

7medium: correct but slows mentors down

How this was checked

I read the code paths that decide what a mentor sees: the data loading, invite/connect and inactivity code in Mentor.jsx; the analytics panels; the E4 store, 待办 grouping and detail page; and the connection RLS in supabase/migrations/001-production-setup.sql.

I then extended the local harness with a fake admin mentor, 9 students covering every case (daily filler, first-month filled or missed, 4 days missing, new and never filled, 邀请中, 已拒绝, 未邀请), and 5 E4 students. The E4 reports are built from the real Leo and Catherine protocol fixtures. Every screenshot below comes from that harness, so no production login or data was involved.

Findings

What's wrong, in order of harm

High

The analytics can't see letter grades, so they report missing feedback that isn't missing

Student v2 saves 客观评价 as a letter in grade_label with score empty. The diagnosis, practice average, per-subject score rule and the E4 过程报告's 客观 stats only count numeric score. In the harness, the practice card says 8 客观评价 while the diagnosis right below says 0 of 10 and raises a red alert. N/A is also counted as a 客观评价. Fix: one shared objectiveOf(row) helper that reads letters, keeps old numeric rows working, and leaves N/A out of both sides of the ratio.

Mentor 数据分析 + E4 过程报告DeepDivePanels.jsx · DimensionStrip.jsx · e4ProgressData.jsWS-A
High

Any mentor account can connect itself to any student without the student accepting

The insert policy on teacher_student_connections checks the teacher but not the status. Admin auto-connect writes status = 1 directly from the browser, and any other mentor account could do the same through the API and then read that student's records. Fix: only admins may insert status = 1; everyone else can only create an invite.

Database policyschema.patch-mentor-connections.sqlWS-C
High · verify first

断开连接 probably does nothing, and re-inviting never works

No policy in the production setup lets a teacher update a connection, so the disconnect update most likely matches no rows. Supabase doesn't report that as an error, so the toast says 已断开 and the next reload shows 已连接 again. The button to re-invite a student who said no tries to insert a second row for the same pair, hits the unique key, and shows 「该学生已经被邀请过了」. Fix: two small database functions, 断开 and 重新邀请, that fail loudly. The SQL file starts with a read-only query, so you can confirm the current policies before changing anything.

Medium

The student list is everyone, newest signup first

A mentor lands on up to 500 student profiles, other mentors' students included, with no "needs attention" order. Fix: default to 我的学生 sorted by days without a record; admin keeps 全部. The new 今日 tab becomes the landing view.

Accounts younger than 7 days with no records are never flagged. 刘佳琪 signed up 5 days ago and has never logged anything, yet her card is clean. The first-month rule handles her separately.

AI 监督流程

The rules the job follows

These are your rules with the four decisions from earlier applied: drafts for mentors only, summaries on this page only, first month counted from signup, and a nightly job that saves the drafts. Dates are Shanghai dates.

StudentWhenFilled inDidn't fill in
Days 0–29 after signupEvery morning, for yesterdayOne sentence of praise tied to a specific recordListed under 昨天未填写
Day 30 onwardMonday, for last Mon–SunA short paragraph: what went well, then any problem the records actually showNo draft; listed under 连续 3 天以上未填写 once yesterday and the two days before are all empty

Filled means at least one record dated that day. A 练习 still waiting for its 客观评价 counts as filled, and the draft can mention it.

What the model sees: that period's records (course, 学/复/练, 主观, 客观 or 待补填, notes, duration) and the existing student stats, without the student's name. It returns the text plus the ids of the records it relied on, so you can check the praise is real. It is told never to set minute targets, compare students, or judge rest days.

How it runs: a new endpoint with its own 15-minute cron, separate from the push reminders. Each call writes at most 15 drafts and is safe to repeat, so a student who fills in at 10am still gets their draft that morning. It uses the same DashScope key and model E4 already uses (qwen3.8-flash in your local setup).

Storage: one new table, supervision_drafts. Mentors can read and mark drafts only for their connected students. Only the server writes new drafts. Students can't see the table at all. The exact SQL is in docs/mentor-e4-audit/PLAN.md.

Before production

Testing it on localhost, in four steps

The first three steps need no database access and send nothing to students. Steps 2 and 3 use the real DashScope model through your .env.local key, but only on fake data.

1

Rule tests

Day 29 versus day 30, yesterday filled or not, late fillers, the Monday window, the 3-day rule, and dates around Shanghai midnight.

npx jest -w 3 __tests__/supervision
2

Read the drafts in the terminal

Generates drafts for the fake students with the real model and prints them. This is the fastest way to tune the tone. Nothing is written anywhere.

node scripts/supervision-dry-run.mjs
3

Click through 今日 in the harness

The local harness (already extended for this audit) serves /mentor and /e4 with fake data. 重新生成 calls the real model on the fake records. Add ?role=2 to see what a normal mentor sees.

npx vite --config vite.harness.config.js

Then open http://127.0.0.1:5199/mentor

4

Real data, still not production

Two options, both only with your OK. The dry-run script has a read-only --live mode that prints drafts for a few real students without saving them, though it does send their records to DashScope. Or, after you run the SQL, push a non-main preview branch and let the cron run there for a day before merging.

node scripts/supervision-dry-run.mjs --live --limit 5

  1. Should E4 show each mentor only their own students by default, or keep the shared view?Decides the default of the new 我的 / 全部 switch.
  2. When a mentor re-invites a student who declined, should the student get the invite push again?It would be the same push a first invite sends today.
  3. Keep the minute thresholds in the mentor diagnosis?「日均 < 60 分钟 = 学习时间不足」 and the 30% 自主 警戒线 are mentor-only today, but they read like a minutes goal.
  4. Is it fine that a planned rest day shows up as 未填写?Students can't mark a rest day, so the list can't tell rest from forgetting.
  5. OK to send students' records, without names, to DashScope?E4 already sends meeting minutes there.
